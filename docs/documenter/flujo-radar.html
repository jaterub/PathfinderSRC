02 / Cómo se obtiene la nota

El modelo ponderado existente (P0.18). La descripción de la oferta proporciona requisitos; el CV maestro se usa para contrastar las tecnologías.

45 pts
25 pts
20 pts
10 pts
Nota nueva = puntos técnicos + experiencia + parecido a tus sí/no anteriores + título V1 + 10 extra si hay salario confirmado ≥ 60.000 €.

El resultado se limita a 100. Los puntos no garantizan un lead: después se aplican restricciones.
Las barras representan pesos máximos, no resultados de una oferta real. Tech = 45 × coincidencias / max(requisitos pedidos, 4); años sin dato = 12 puntos; V1 completo 10, parcial V1 5, otras familias 0.

03 / Qué puede cambiar la decisión

Un score alto no implica automáticamente que se recomiende la oferta.

🛑 Presencial

Se descarta por modalidad aunque la nota alcance 60.

🧭 Familia objetivo

Solo V1 puede ser lead. Otros títulos quedan en revisar como máximo, salvo reglas de guardadas.

🧩 Encaje parcial

Una coincidencia parcial se mantiene en revisar.

⏳ Antigüedad / vigencia

Ofertas >60 días o con cierre probable no pueden salir como lead.

🚫 Fuera de rol

Reglas duras descartan; el tope de nota es 20.

⭐ Guardada por ti

Tiene una excepción explícita: prioriza tu elección, respetando la restricción presencial y tus decisiones.

Importante: este es un mapa del código, no un nuevo motor de scoring. La fuente de verdad sigue siendo score_radar.py.

04 / Si algo falla, ¿dónde miro?

Desplegables orientados a quien entra por primera vez al proyecto.

No llega una oferta de LinkedIn
Recorrido: BAT → captador → JSON diario → importador → RAW.
  • Ver lotes y 429: captura_linkedin.py y 3_datos/registros/lotes_log.csv.
  • Test de 30 peticiones, cache y errores: test_captura_linkedin.py.
  • Revisar primero si la oferta está ya deduplicada por ID.
La oferta existe, pero la nota no encaja
Recorrido: RAW + JSON de descripción + CV + feedback → score_offer() → restricciones.
  • Ver fórmula y desglose: score_radar.py:428–605.
  • Ver casos esperados: test_p012_regresion.py.
  • Confirmar si hay descripción; sin datos técnicos la cobertura puede ser 0.
Una descripción aparece cortada en el CSV
Recorrido: descripción JSON → csv_text() → escritura/lectura CSV.
  • Código: score_radar.py:666–679.
  • Test de comas, punto y coma, comillas y saltos de línea: regresión del CSV.
  • PR histórico: #116 — conservar descripción literal.
GitHub Actions falla o no se ejecuta
Recorrido: evento PR → filtros de rutas en YAML → tests Python/PowerShell → resultado.
  • p012-api-email-tests.yml
  • Historial de ejecuciones
  • Que un test pase no demuestra que la regla de negocio sea óptima.

05 / Quién controla cada parte

Diferencia entre el flujo de producción, sus pruebas y las decisiones humanas.

¿Quién inicia la ejecución?
La tarea declarada en CONTEXTO.md es «Profesion Lotes LinkedIn» (lunes a sábado, 11:35, Europe/Madrid). Parte PC: captura en lotes mediante BAT. Parte nube: Gmail y consolidación posterior. La programación efectiva se verifica en el servicio de tareas, no solo leyendo el repositorio.
¿Qué hace GitHub Actions?
El archivo YAML de CI decide cuándo correr pruebas según los archivos modificados en PR o ejecución manual. Ejecuta, entre otros, test_captura_linkedin.py, test_importa_api.py y test_p012_regresion.py. No dispara por sí solo la captura diaria del PC.
¿Dónde viven el check y el Kanban?
Fuente canónica: CONTEXTO.md. Sincronización con Issues / Projects: workflow de jerarquía. La lectura del código no verifica por sí sola el estado real del tablero.
¿Qué aporta Javier?
Edita las columnas ok y razon en 1_panel/radar.csv. Esas decisiones vuelven a entrar en la siguiente pasada y alimentan la comparación de títulos. El pipeline registra candidaturas y eventos; una recomendación automática no equivale a una candidatura enviada.
¿Qué documentaría el agente Documenter?
Cada sección conservaría: propósito → entrada → código → prueba → automatización → evidencia → diagnóstico. Este documento es solo una propuesta de presentación; no hay un agente Documenter desplegado aquí.

Referencias del prototipo de origen

Esta documentación describe el prototipo de Profesión. Sus rutas de código, pruebas, datos y automatizaciones se conservan como referencias documentales. Esas piezas pertenecen al proyecto privado y todavía no están migradas al repositorio público; por eso los enlaces del inspector y las citas llevan a esta nota.
